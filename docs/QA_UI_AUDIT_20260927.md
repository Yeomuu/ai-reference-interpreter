## 발견한 남은 문제

- 데스크톱 폭에서 `07 결과`를 열어 둔 채 브라우저를 390px로 줄이면 가로 단계 탐색이 초기 위치에 남아 현재 단계가 화면 밖에 있다. 390px에서 단계를 직접 누르면 현재 단계로 이동한다. `App.tsx`의 단계 탐색 스크롤 처리를 뷰포트 폭 변경에도 적용해야 한다. 해당 파일은 API 작업과 충돌하지 않도록 이 점검에서 수정하지 않았다. [`10-results-390.png`](qa-evidence/ui-audit-20260927/10-results-390.png)
- 현재 검토 우측 요약은 길어서 실행 버튼이 1440×900 첫 화면보다 아래에 있다. 실행을 위한 무리한 고정 버튼보다, 실제 생성 비용·샘플 구분과 실행 결과를 버튼 바로 앞에 알리는 편이 적합하다. API UI 담당자에게 전달했다.

## 이번 수정과 확인

- `src/styles/app.css`에서 작업 도면의 최소 높이를 320→300px로 줄였다. 1280×800에서 도면 전체 조작면이 하단 바 위에 남는다.
- 767px 이하에서 목록·속성·요소·결과·구조 편집의 내부 최대 높이와 중첩 세로 스크롤을 해제했다. 도면 아래의 중복 보조 도움말만 숨겼고, 도면 자체의 조작 설명과 범례는 유지했다.
- 수정 후 390px에서 목록과 속성이 자연스러운 문서 스크롤로 이어지고 가로 본문 넘침은 없음을 확인했다. 768px에서 도면은 양쪽 패널보다 위의 전체 폭 행을 차지한다.

## 같은 날 후속 기획 재검토

위 표의 ‘공간 자료 양호’ 판정은 도면 출처와 사진 분리에 한정된다. 구조·영역 탭이 캔버스를 숨기고 좌표값만 입력하게 한 점은 직접 조작 기획에 맞지 않았다. 후속 수정에서 캔버스를 항상 보이게 하고 기둥·기존 등은 클릭, 벽·개구부는 선 드래그, 바닥·공간·천장·동선은 사각형 드래그로 등록했다. 기존 검증에 걸리는 가벽은 저장하지 않고 충돌 이유를 표시했다. 좌표 입력은 펼칠 수 있는 키보드 대안으로 남겼다.

도면 설명이 패널 왼쪽 경계에 붙은 문제는 Space 패널의 도면 전체에 16px 좌우 여백을 주어 고쳤다. 768–1199px에서는 도면을 사진보다 먼저 전체 폭으로 배치했다. 후속 브라우저 확인에서 1440×900의 도면 끝은 832px, 하단 바 시작은 835px였고 1280×800은 각각 732px와 735px였다. 390px의 본문 너비는 뷰포트 390px을 넘지 않았다. 이 값은 이번 수정본의 측정이며 위 표의 과거 캡처 판정을 소급 변경하지 않는다.

## 2026-09-28 후속 상태

결과 화면에서 추가 시점을 만들 때도 시점 편집과 같은 유효 바닥 탐색을 사용한다. 생성 기준 기존 사진 선택, 부분 레퍼런스 픽셀 자르기, 화각을 포함한 이전 조건 판정, 불확실한 유료 요청의 재시도 잠금, 생성 후 저장 실패 시 이미지 내보내기와 재저장을 코드·자동 테스트로 확인했다. 수평 단계 탐색에는 `ResizeObserver`로 현재 단계를 다시 가운데에 맞추는 처리가 있다. 이 날짜의 새 브라우저 연결은 실행 환경 오류로 열리지 않아 이 후속 변경의 데스크톱·모바일 시각 재검사는 완료했다고 기록하지 않는다. 위 표와 수치는 2026-09-27 로컬 브라우저 검증 결과다.
