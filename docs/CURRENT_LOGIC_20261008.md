# ReSpace 현재 기능·검증 로직 설명 · 2026-10-08

현재 구현의 동작을 코드에서 확인한 문서다. 화면 설계 제안이나 실측·시공 가능성 판정이 아니다. 실행한 QA와 수정 내역은 `QA_LOGIC_20261008.md`, 디자인 비교는 `QA_FIGMA_ALIGNMENT_20261008.md`, 폰트·이동 버튼 검증은 `QA_TYPOGRAPHY_NAVIGATION_20261008.md`에 분리해 기록한다.

## 1. 프로젝트와 저장

- 기존 React 19·TypeScript·Vite 프로젝트를 유지한다. 네 단계는 공간·방향 설정 → 레이아웃 구성 → 레퍼런스 적용 → 시안 생성이다. 시점 편집·생성 전 확인·결과 확인은 모두 4단계에 속한다. 기존 keep/camera/review/results 직접 URL도 유지한다.
- 홈의 프로젝트 이름·공간 유형은 기본값을 수정할 수 있다. 참가자 번호는 P 뒤 숫자 2~4자리다. 유효한 세 값을 입력하면 과업 A 기록과 새 학교 프로젝트를 준비한다. 같은 참가자의 진행 중 프로젝트는 이어가며, 사용자가 건드리지 않은 홈 기본값으로 저장된 이름을 덮어쓰지 않는다.
- 새 학교 프로젝트에는 실제 공간 사진 2장, 참고 이미지 3장, 제공 개략 도면이 있다. 배치 요소·레퍼런스 연결·카메라·결과는 비어 있다. 사진에서 구조나 가구를 자동 추출하지 않는다.
- 저장한 프로젝트·일반 공간·기존 샘플은 홈의 목록에서 접근한다. 일반 새 프로젝트는 도면 없이 시작할 수 있다. 2단계의 빈 도면 상태에서도 사이드바 이동 버튼과 공간 설정으로 돌아가는 버튼을 제공한다.
- 프로젝트 메타데이터는 localStorage, 업로드/생성 이미지 파일은 IndexedDB에 보관한다. 서버에 전체 프로젝트를 자동 동기화하는 계정 서비스는 없다. 같은 브라우저 프로필·사이트 origin에서 이어간다.
- 저장 데이터의 타입·필드·좌표·참조 구조를 검사한다. 구형 레이아웃/카메라 마이그레이션은 기존 ID·좌표·결과 스냅샷을 보존하는 추가 방식이다. 손상되거나 지원하지 않는 원본 데이터를 정상 프로젝트인 것처럼 덮어쓰지 않는다. 저장 실패는 화면에 표시하고 새 유료 생성을 막는다.
- 단계 URL은 History API를 사용한다. 뒤로/앞으로·새로고침·직접 URL 접근에서 저장된 프로젝트를 복원한다. 단계 이동은 데이터를 초기화하지 않는다.

## 2. 사진·참고 이미지·도면의 차이

| 자료 | 역할 | 하지 않는 일 |
|---|---|---|
| 실제 공간 사진 | 현재 외관·창·문·벽 등 생성의 기준 사진 | 사진만으로 정확한 평면도/치수를 만들지 않음 |
| 참고/분위기 이미지 | 선택한 모양·색·재료·조명 특성 | 사진 속 공간의 구조를 실제 공간 좌표로 간주하지 않음 |
| 상품 이미지 | 상품 외관의 참고 | 그 이미지 자체를 바닥의 독립 구조로 놓지 않음 |
| 도면 | 구조·배치·시점을 지정하는 유일한 2D 작업 기준 | 개략도를 실측 CAD나 3D 모델이라고 주장하지 않음 |
| 생성 시안 | 특정 시점·당시 조건의 이미지 결과 | 현장 설치와 구조 정확성을 자동 인증하지 않음 |

- PNG/JPEG/WebP만 받는다. 확장자·MIME·실제 파일 시그니처·빈 파일·크기를 확인하고 이미지 디코딩을 통해 크기를 읽는다. 일반 사진/레퍼런스는 12MiB, 도면은 20MiB 이하이다.
- 도면을 올리면 원본 이미지 가로세로 비율을 유지한다. 구조 자동 인식은 없다. 사용자가 바닥 윤곽을 직접 표시하고 구조·영역·보존·배치를 확인해야 한다.
- 일반 프로젝트의 도면 교체는 기본적으로 이전 구조/영역/보존 표시를 비우고 현재 요소의 위치를 해제한다. 전체 공간 조건은 유지한다. 요소 자체와 과거 결과를 삭제하지 않는다. 삭제 복구를 제공한다.
- ‘기존 표시 유지 후 새 도면에 맞추기’는 명시적인 대안이다. 구조·영역·배치를 보존하지만 도면 대응 확인은 여전히 필요하다. 바닥 윤곽이 없으면 확인 완료 버튼을 사용할 수 없다. `planAlignmentPending`이 남아 있으면 생성은 불가하다.
- 도면이 없으면 가로/세로 개략도 또는 빈 도면에서 직접 그린 다각형을 시작한다. 곡선은 다각형 근사이며 사진에서 측정하지 않는다.
- 새 학교 참가자 시나리오의 기준 사진·도면은 고정 자료다. 일반 프로젝트의 사진/도면 업로드는 계속 제공한다.

## 3. 보존된 벽에 무엇을 붙일 수 있는가

보존은 벽 자체의 위치·형태·존재를 유지한다는 뜻이다. 호환되는 장식까지 모두 금지하지 않는다. `base/partition`이라는 구조 출처와 보존 잠금은 별개의 값이다.

| 작업/요소 | 보존된 벽 | 추가로 검사하는 것 |
|---|---|---|
| 벽 이동·삭제·교체 | 불가 | 일반 구조는 잠금 해제 후에도 충돌 검사를 받음 |
| 탈착식 벽 그래픽·포토존 | 허용, 반복 확인 대화상자 없음 | 창/문/출입구 구간, 같은 면의 다른 물리 부착물 |
| 벽 조명·벽 부착 상품·기타 벽 부착물 | 허용하되 고정 방식/손상 여부를 직접 확인하라는 경고 | 같은 개구부·부착물 충돌 |
| 벽 마감/재질 교체 | 불가 | 보존 해제 가능한 일반 벽에서만 재질 조건 적용 가능 |
| 벽과 무관한 천장 조명 | 천장 위치에 허용 | 기존 천장 조명·다른 천장 요소와 점유 위치 검사 |
| 기존 천장 조명의 색감 | 조명 구조에 한해 변경 가능 | 조명 구조 자체의 이동 잠금과 구분 |

- 새 참가자 프로젝트의 앞/뒤/창문/출입문 쪽 벽, 출입문, 종속 창 2개에는 `preservationRequired`가 있다. 이 구조는 잠금 해제·이동·삭제·형태 변경이 불가하다. 화면에는 5개 기본 그룹을 표시한다. 저장된 기존 프로젝트를 자동으로 다시 잠그지 않는다.
- 일반 구조의 보존은 사용자가 끄고 켤 수 있다. 껐다는 사실은 다시 불러오기/마이그레이션 후에도 유지한다. 보존 설명과 표면 허용 메타데이터를 보존한다. 잠금 해제는 실제 철거나 이동 가능성을 검증했다는 뜻이 아니다.
- 부모 벽을 옮길 때 연결된 창/문의 잠금이 켜져 있으면 먼저 해제해야 한다. 허용된 벽 이동은 연결 개구부를 함께 이동시킨다. 창·문은 연결된 벽을 따라 이동하며 자유로운 바닥 이동으로 바뀌지 않는다. 연결 개구부가 있는 벽의 끝점 변경은 제한한다.
- 고정 벽 선택은 오른쪽 속성 패널을 연다. 장식 도구를 선택했을 때만 부착물을 추가한다. 기본 잠금 아이콘을 눌러도 필수 구조의 잠금은 풀리지 않는다.
- 추가 가벽은 A/B면을 구분한다. 반대 면 부착물의 겹침은 허용하지만 같은 면 겹침은 거절한다. 면 정보가 없는 구형 부착물은 보수적으로 겹침 검사하며, 생성 전에 가벽의 부착 면을 지정해야 한다.
- 벽면 요소의 최초 추가 구간은 기본 범위다(그래픽 10~25%, 벽 조명 10~20%). 실제 부착 구간은 속성 편집기/벽을 따른 이동으로 조정한다. 클릭 위치를 실측 부착 좌표로 자동 변환했다고 해석하면 안 된다. 같은 구간을 다시 사용하면 충돌이 날 수 있다.

## 4. 요소 타입과 허용 위치

| 요소 | 허용 앵커 |
|---|---|
| 전시대·테이블·의자·기타 바닥 물체 | 바닥 점 또는 타입이 허용하는 바닥 영역 |
| 스탠드 조명 | 바닥 점 |
| 벽 그래픽·포토존·벽 조명·벽 상품·벽 재질·기타 벽 물체 | 벽 구간 |
| 천장 조명·매달린 전시물·기타 천장 물체 | 천장 영역/영역 안의 점 |
| 진열 상품 | 전시대·가구의 표면 |
| 공간 조명 분위기·색감·기타 공간 조건 | 전체 공간 또는 허용된 지정 영역 |
| 바닥 재질 | 바닥 영역 |

- 호환되지 않는 앵커는 거절한다. 적용 제외된 요소는 배치할 수 없다. 실패한 이동·회전·크기 변경은 이전 데이터로 남는다.
- 바닥 물체는 중심과 footprint(폭/깊이), 회전을 갖는다. 사용 가능한 바닥 안에 전체 점유 범위가 들어가는지, 벽·기둥·문 여닫이 여유·통행 동선·다른 바닥 물체와 겹치는지 검사한다. 사각/원 기둥, 다각형 바닥도 검사한다. 회전 footprint는 보수적인 점유 범위를 사용한다.
- 물리 물체를 영역 전체에 놓는 경우 영역의 적합성도 검사한다. 비사각 물리 점유는 바닥 점+footprint로 지정하도록 제한한다. 바닥 재질은 가구와 같은 점유 층이 아니어서 가구와 함께 존재할 수 있지만, 같은 재질 층끼리 중복되는 범위는 검사한다.
- 천장과 바닥은 별도의 점유 층이다. 천장 조명은 테이블 위에 있을 수 있다. 영역 내 서로 다른 offset은 허용하며 같은 천장 위치·기존 천장 조명과 겹치면 거절한다. 점유 크기 정보가 없는 구형/기타 천장 요소는 연결한 영역 전체를 사용해 보수적으로 검사한다.
- 공간 분위기 영역은 색·재료·조명 범위이고 통행 동선은 비워 둘 범위다. 분위기에 통행 동선을 적용 대상으로 제공하지 않는다. 도면의 영역 선이 물리 벽을 가로지르는 경우 관련 그리기 검사를 적용한다.
- 요소 위치 고정은 구조 보존과 별개다. 고정한 요소의 이동/회전/크기 변경/삭제 UI는 막지만 레퍼런스 외관 연결은 가능하다.

근거: `src/domain/validation.ts`, `geometry.ts`, `drawing.ts`, `movementFeedback.ts`, `areaTargets.ts`, `src/components/PlanCanvas.tsx`.

## 5. 전시대와 진열 상품

- 적용 중인 전시대/가구만 받침이 될 수 있다. 받침 위치가 없으면 ‘위에 놓기’ 버튼을 비활성화한다. 상품은 자기 자신이나 없는 받침, 부적합한 물체를 받침으로 선택할 수 없다.
- 상품에는 받침 ID와 표면 안의 0~1 상대 좌표를 저장한다. 받침/상품의 겹침은 의도한 관계이므로 바닥 충돌로 거절하지 않는다. 고정된 전시대 위에도 상품을 추가할 수 있다.
- 전시대 이동/회전 시 상품의 표시 위치는 같은 받침·상대 좌표에서 계산된다. 전시대 삭제/적용 제외/받침이 될 수 없는 타입 변경 시 상품은 삭제되지 않고 받침 위치를 해제한다. 과거 결과도 남는다.
- 상품 표시를 눌러 같은 받침 위에 여러 상품을 추가할 수 있다. 상품끼리의 적층·높이·실제 포장 치수는 측정하지 않으므로 실제 적재 가능성까지 검사했다고 주장하지 않는다.

근거: `src/domain/display.ts`, `revisions.ts`, `src/components/PlanCanvas.tsx`, `src/services/planGuide.ts`.

## 6. 레퍼런스 연결·변경·삭제

- 레이아웃은 참고 이미지 없이도 먼저 만들 수 있다. 전체 이미지 또는 사용자가 선택한 crop을 클릭/드롭으로 한 개 또는 여러 대상에 연결한다. crop은 이미지 안의 유효한 비율 사각형이어야 한다.
- 외관/형태, 재료, 조명 분위기는 구분한다. 가구가 포함된 선택에 조명 해석을 함께 적용하는 등 한 대상이라도 부적합하면 전체 묶음 연결을 거절하며 일부만 몰래 적용하지 않는다.
- 벽·영역·전체 공간 선택으로 만든 연출 조건은 `mapping-condition`이다. 실제 벽을 복제하거나 새 전시대를 만들지 않는다. 독립 배치 요소는 `layout`이다. 이 차이가 연결 해제·삭제 동작을 결정한다.
- 독립 가구/부착물의 연결 해제: 외관 출처와 crop을 비우고 위치·크기·회전·상품 받침을 유지한다. 조건만으로 생긴 벽/공간 연출의 연결 해제: 해당 파생 조건을 제거하고 원래 벽/영역은 유지한다.
- 이미지 삭제: 현재 참고 이미지/연결/파생 조건을 정리한다. 독립 배치 요소는 외관 연결만 해제한다. 개별 요소 삭제: 그 요소와 연결의 해당 ID를 정리하지만 원본 참고 이미지는 삭제하지 않는다.
- 과거 시안의 조건/이미지/참고 출처는 보존한다. 구형 결과에 원본 메타데이터가 없으면 삭제 전에 당시 출처를 저장한다. 동일 파일을 다른 참고 이미지가 사용하면 현재 파일도 유지한다.
- 현재 프로젝트, 결과 스냅샷, 편집 기록, 삭제 복구에서 쓰는 이미지 파일은 제거하지 않는다. 복구 가능 데이터가 없는 사용 종료 파일만 정리 후보로 다룬다.

근거: `src/domain/layoutMapping.ts`, `revisions.ts`, `src/app/App.tsx`의 applyMapping/commitDeletion 및 자산 보관 effect.

## 7. 실행 취소·다시 실행·삭제 복구

- 현재 탭의 일반 편집은 프로젝트별 최근 50개 상태로 Ctrl+Z/Ctrl+Shift+Z 및 도면 버튼에서 실행 취소/다시 실행한다. 새 편집은 redo 이력을 비운다. 이 일반 편집 스택은 메모리에 있어 새로고침 후 전체 스택이 살아 있다고 주장하지 않는다.
- 마지막 삭제/도면 교체의 복구 patch는 별도 localStorage 기록이다. 같은 프로젝트·삭제 직후 commonRevision일 때만 불러온다. 재접속/새로고침 후 알림이 사라져도 도면 실행 취소 버튼 또는 Ctrl+Z로 복구한다.
- 후속 공통 조건 수정 이후 오래된 삭제 patch로 새 작업을 덮어쓰지 않는다. 잘못된 복구 스키마·허용하지 않는 필드·손상된 요소는 무시하고 원시 기록을 자동 덮어쓰지 않는다.
- 삭제 복구 기록을 저장할 수 없으면 삭제를 시작하지 않는다. 복구 기록을 준비한 뒤 프로젝트 저장이 실패하면 이전 복구 기록으로 롤백한다. 삭제 복구는 과거 시안 조건을 되돌려 쓰거나 삭제하지 않는다.
- 2단계에서 선택 배치 요소는 Backspace/Delete로 삭제 가능하다. 입력창·숫자/이름 편집·연속 키 반복·그리기 동작을 보호하며, 구조/영역과 다른 단계에 같은 삭제 단축키를 무분별하게 적용하지 않는다.

근거: `src/app/App.tsx`의 editState/restoreEdit/commitDeletion/undoDeletion/deleteLayoutSelection, `src/services/deletionUndo.ts`.

## 9. 시점과 조건 변경

- 첫 4단계 진입 때 전체 배치/입구에서 안쪽/다른 방향 추천 시점을 준비한다. 카메라는 실제 바닥 안의 벽·기둥·가구·문 충돌을 피하는 위치를 탐색한다. 자동 추천을 사용자가 수정하면 그 수정을 보존한다. 추천이 없는 것과 삭제한 사용자 시점을 구분한다.
- 시점 이름·바닥 좌표·방향·화각·높이·상하 각도를 수정한다. 전체 배치 기본값은 높이 3.2m, -45°의 높은 사선 시점이다. 여성 1.48m/남성 1.60m 눈높이 옵션은 코드에서도 ‘임시’ 값으로 표시하며 검증된 인체 평균이라고 주장하지 않는다.
- 카메라 삭제는 과거 결과를 지우지 않는다. 남은 첫 시점을 대표로 정리하고 관련 결과는 오래된 조건 표시를 유지한다. 시점 삭제도 일반 편집 실행 취소 대상이다.
- 공통 공간/배치/레퍼런스 변경은 commonRevision을 올리고 기존 결과를 stale로 표시한다. 카메라 위치·방향·화각 등 변경은 해당 시점 결과를 stale로 표시한다. 이름만 바꿨다고 모든 이미지의 구조를 다시 쓰지 않는다. 원래 이미지를 몰래 재생성/수정하지 않는다.

근거: `cameraRecommendations.ts`, `cameraDefaults.ts`, `revisions.ts`, `validation.ts`, `prototypeConfig.ts`.

## 10. 생성 전 검사·실제 요청·부분 실패

- 기존 공간 사진, 도면, 도면 대응 확인, 존재하는 보존 구조, 유효한 대표/선택 카메라, 적용 요소와 위치, 필요한 레퍼런스/파일, 가벽 면, 모든 배치 충돌을 검사한다. 오류는 생성 불가, 벽 부착 방식 같은 경고는 확인 안내다. 참고가 없는 독립 기본 레이아웃도 가능하지만 출처가 필요한 파생 조건을 빈 출처로 생성하지 않는다.
- 입력은 기존 공간 사진 1장 → 당시 저장 도면/구조/배치/선택 시점 가이드 → 적용 레퍼런스 순이다. 원본 도면 이미지는 가이드 배경으로 보존한다. 다수 참고 이미지는 최대 3개의 bounded contact sheet에 포장하며 추가 모델 호출을 만들지 않는다. 각 원본/crop manifest를 검사한다.
- 생성 payload는 최대 이미지 5개, 이미지당 550,000bytes, body 4,000,000bytes, prompt 16,000자다. 길이를 안전하게 줄인 뒤에도 초과하면 POST 전에 거절한다. 서버에서도 스키마·기존 사진·선택 시점·스냅샷·도면 가이드·crop/source manifest를 다시 검증한다.
- 현재 설정은 `gpt-image-1-mini`, low, 1536×1024 JPEG 1장/요청이다. API 키는 서버 환경 변수만 읽는다. 사용자가 별도 참가자 키/초대 코드를 입력하지 않는다. 이 QA는 실제 모델을 실행하지 않았으므로 이미지 품질을 보증하지 않는다.
- 여러 시점은 순차 처리한다. 시점마다 다른 UUID·도면 가이드로 요청하고 결과를 하나씩 저장한다. 사이에 서버 가능 상태만 확인하며 유료 POST를 자동 재시도하지 않는다. 첫 이미지 이후 실패하면 첫 결과를 유지하고 남은 시점을 중단한다. 일괄 처리 전체 동안 재클릭을 막는다.
- 네트워크/응답이 불확실하면 sessionStorage에 시각을 남기고 최소 180초 재요청을 잠근다. 이후에도 사용자가 위험을 확인하고 재시도를 허용해야 한다. 새로고침만으로 즉시 재요청하지 않는다.
- 이미지가 이미 생성됐는데 로컬 저장이 실패하면 탭 메모리에 결과를 보존하고 내보내기/저장 재시도를 안내한다. 실패를 성공 저장으로 보고하지 않는다.
- 일반 샘플은 미리 제공된 이미지임을 명확히 표시한다. 현재 조건이나 카메라로 실제 생성된 결과가 아니다. 학교 시나리오에는 그 공간의 사전 생성 결과가 있다고 꾸며 보여주지 않는다.

근거: `src/services/imageProvider.ts`, `generationContract.ts`, `generationQueue.ts`, `planGuide.ts`, `planGuideImage.ts`, `api/generate.ts`.

## 11. 공유 생성 한도

- 한국 자정 기준 서비스 전체 60회/일, 서명된 익명 브라우저 20회/일이다. 참여자 번호·IP·계정별 한도가 아니라 HttpOnly/SameSite=Strict 서명 쿠키의 브라우저 식별자다. 쿠키 삭제 후에도 개인 한도가 절대 우회 불가하다고 주장하지 않는다. 전체 한도는 공유 원장이 제한한다.
- Production/Preview가 같은 private Blob 저장소를 사용하도록 구성하는 계약이며 코드의 원장 경로는 공통이다. 실제 환경별 연결은 이번 QA에서 재검증하지 않았다. UUID replay claim과 조건부 쓰기/동시 처리 lease로 예약하고 모델을 호출한다. 예약 저장 장애·한도 소진·재전송은 모델 호출 전에 거절한다.
- 접수된 요청은 실패해도 사용량을 환불하지 않는다. 배포·공개 요청으로 원장을 리셋하지 않는다. 서버 시각의 한국 자정에 일별 사용량을 바꾸며 이전 UUID 재전송 방지 기록은 유지한다. 기존 원장 마이그레이션도 기록을 보존한다.
- 3개 시점을 실제 접수하면 3회 차감된다. 일부 실패한 요청에도 비용이 발생할 수 있어 무조건 남은 시점을 다시 호출하지 않는다. 이번 QA에서는 원장/모델 동작을 mock으로 검사했으며 live Blob 경쟁/실제 차감은 실행하지 않았다.

근거: `api/_lib/generationQuota.ts`, `generationIdentity.ts`, `api/status.ts`, `api/generate.ts`.

## 12. 결과·내보내기·실험 기록

- 각 결과에 카메라·공통 버전·보존 구조·요소/위치·참고 이미지/crop·디자인 목표·기준 사진·생성 시각 스냅샷을 보관한다. 현재 레퍼런스/카메라 삭제나 배치 변경 후에도 그 당시 조건을 확인한다. 조건 대조 도면도 그 스냅샷을 사용한다.
- 결과 유지 선택과 이미지 내보내기는 사용자 동작이다. AI 제안은 자동 확정 배치로 반영하지 않는다. 현재 작업에서 삭제된 요소의 과거 기록은 보이지만 사라진 요소를 수정하는 버튼은 제한한다.
- 작업 기록 JSON과 결과 이미지 다운로드를 제공한다. JSON의 `asset://` 식별자는 이 브라우저의 파일을 가리키므로, JSON만 다른 기기에 옮겨 모든 원본 이미지가 자동 복원된다고 주장하지 않는다.
- 선택적인 실험 기록은 structured 조건의 로컬 세션/이벤트·초기/최종 조건·JSONL/CSV/JSON ZIP이다. A 종료/B 시작, 완료 세션의 6개 문항 1~5 응답을 보관한다. 서버 자동 제출, free-text 비교 UI, 완료된 ground truth, 사람의 정확도 코딩은 구현됐다고 주장하지 않는다.
- 원본 파일명·이미지·키 입력·API 키를 이벤트에 수집하지 않는다. 최종 평가 조건에는 사용자가 작성한 문장이 포함될 수 있으며 내보내기 안내에서 알린다. `ts_server`는 서버 수집이 없어 null이다. 로그 지표가 조건 정확도 점수를 대신하지 않는다.
- 가이드는 새 탭/다운로드로 제공한다. 원래 실제 기능·데이터·비용 제한은 이번 폰트/색상/버튼 위치 변경에서 유지한다.

근거: `src/app/App.tsx`의 renderResults, `src/services/experiment.ts`, `src/components/ExperimentPanel.tsx`, `src/services/zip.ts`.

## 13. 디자인과 이번 QA의 경계

사용자가 수정한 Figma 진행 아이콘/색상을 읽기 전용으로 가져왔다. Figma 문서를 수정하는 작업은 하지 않았다. 폰트 배포 금지를 철회한 최신 지시에 따라 검증된 제공 Paperlogy 400/500/600/700/800을 원본 그대로 public/fonts에 포함했다. 개발과 production은 같은 폰트 CSS/파일을 읽는다. 캡션 12, 보조 14, 본문 16, 진행/섹션 18, 일반 제목 20~22px의 사용자 승인 역할 토큰을 적용했다. 홈의 큰 브랜드/소개 문구는 별도 표시 역할이다. Wanted Sans, 제공 브랜드 fallback, 공식 Adobe/Noto 공급 방식은 유지한다.

단계 이동은 공통 컴포넌트로 각 사이드바 하단에 고정한다. 속성 패널을 사용자가 숨긴 시점 편집에서는 이동을 잃지 않도록 외부 fallback을 표시한다. 작은 화면은 패널을 이어 쌓는다. 실제 폰트 HTTP/디코딩/브라우저 사용 글꼴과 화면 캡처를 검사했다.

이 설명은 현재의 정규화된 2D 규칙과 UI 동작을 다룬다. 측량, 구조 안전, 벽 고정 방식, 상품 적재, 조명의 광학/3D 가림, 모든 모델 시안의 공간 일치는 자동으로 검증하지 않는다. 실제 기기 Safari/Android, 스크린 리더 인증, live 유료 생성은 이번 QA 범위 밖이다. 실행 범위와 남은 항목은 QA 문서에 명시한다.
